    Deploy¶

    Everything in deploy/ is for running the simulator as a service: one GPU server, and recording clients wherever the people are. This page helps you choose a layout. The pages after it walk through each part.

    deploy/
├── server/
│   ├── start_server.sh / .bat   # launch the server with the right environment
│   ├── gnss-server.service      # systemd unit (Linux)
│   ├── start_telemetry.sh       # Prometheus + Grafana via docker compose
│   ├── prepare_rinex.py         # fetch a navigation file on a connected machine
│   └── requirements_server.txt  # pinned dependency list for mirror installs
└── client/
    ├── deploy_client.py         # the recording client
    ├── run_pocketsdr.py         # optional: track a recording with PocketSDR
    └── requirements_client.txt  # numpy, pyzmq

    Choose a layout¶

    • One workstation

      Server and client on the same GPU machine. The simplest layout, and the fastest: frames can pass through shared memory with no network copy.

      For: individual developers, benchmarking.

      Quickstart

    • Shared GPU server

      One Linux GPU host runs the server as a service. Engineers record from their own laptops with a two-package client over TCP.

      For: teams, labs, test benches.

      GPU server · Recording client

    • Cloud GPU

      A rented GPU pod (RunPod, or any CUDA VM). Run the client on the pod and copy the results back, or tunnel port 5555 over SSH.

      For: occasional large runs, trying hardware before you buy it.

      Cloud notes

    • Air-gapped network

      No internet on the server. Packages come from an internal mirror, navigation files and updates by hand.

      For: classified or isolated labs.

      Air-gapped networks

    What lives where¶

    The client sends only the scenario YAML. Everything else is read on the server, relative to the directory the server started in:

    Item Lives on Notes
    Scenario YAML client Sent as text with each INIT, so you can edit it locally.
    simulator_params.yaml server Sample rates, carriers, frame timing, atmosphere models. Fixed when the server starts: restart it to change them.
    RINEX navigation files server Searched for in data/rinex/ and tests/data/. Clients can upload one.
    Emitter CSV, trajectory CSVs, antenna pattern files server Paths in the scenario are resolved on the server, so the files must exist there.
    Recordings client Written by the client wherever --output points.

    A scenario that works locally can fail remotely

    If your scenario names config/my_jammers.csv or a trajectory file, copy that file to the same relative path on the server. The scenario travels to the server; the files it points to don't.

    Ports¶

    Port Service Needed
    5555/tcp Simulator (ZeroMQ request/reply) Always. Override with GNSS_PORT.
    8000/tcp Server Prometheus metrics For monitoring
    3000/tcp Grafana dashboards For monitoring
    9090/tcp Prometheus UI For monitoring
    9100, 9400/tcp Node and GPU (DCGM) exporters For monitoring, local to the host

    How sessions work¶

    • One client at a time. The first client to send INIT owns the session. Others get BUSY until it sends STOP. STATUS and RINEX uploads are always answered.
    • Abandoned sessions expire. After 120 s with no requests from the owner, the server releases the session and frees the GPU. A crashed client doesn't lock the server for long.
    • The server outlives sessions. STOP releases the GPU and returns the server to IDLE. Only SHUTDOWN, Ctrl+C or the service manager stops the process.

    The simulator port has no authentication

    Anyone who can reach port 5555 can start runs, upload files into data/rinex/, and shut the server down. Open it only to trusted machines: a lab VLAN, a firewall allow-list or an SSH tunnel. Never expose it to the internet.

    Transport: zmq or shm¶

    The server returns frames in one of two ways, chosen with --transport when it starts:

    zmq shm
    Frames travel over the ZeroMQ socket through shared memory; only metadata on the socket
    Client location anywhere same machine only
    Used by start_server.sh / .bat (default) python -m gnss_sim.framework.server (default)

    deploy_client.py detects which one the server uses, so the same command works with both. If clients connect from other machines, start the server with zmq, which the start scripts do.

    Cloud GPU¶

    On a RunPod pod (or similar):

    bash scripts/setup_env.sh          # first time only; keeps the env on fast local disk
source scripts/runpod_init.sh      # every session: CUDA 12.9 libs, paths, activation
./deploy/server/start_server.sh

    You can reach the server in two ways:

    • Record on the pod, then copy the results back with scp or rsync. This is the fastest option, because 98 MB per second of signal per stream doesn't have to cross the internet live.
    • Tunnel: run ssh -N -L 5555:localhost:5555 <pod> on your machine, then deploy_client.py --host 127.0.0.1. The port stays private.
