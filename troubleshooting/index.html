    Troubleshooting¶

    Problems grouped by where they show up. Most come down to three things: the GPU stack, the network path to port 5555, and files that exist on one machine but not the other.

    GPU and CUDA¶

    Symptom Cause and fix
    nvidia-smi: command not found No NVIDIA driver. Install 535 or newer and reboot.
    import cupy fails, or CUDA driver version is insufficient The driver is older than CUDA 12. Update the driver. cupy-cuda12x brings its own runtime, so the toolkit doesn't matter.
    no kernel image is available for execution on the device, or NVRTC errors on an RTX 50-series or Blackwell GPU The runtime is too old for compute capability 12.0. Install the CUDA 12.9 libraries and start the server with start_server.sh, which puts them on LD_LIBRARY_PATH.
    The first run sits at COMPILING_KERNELS for minutes Normal on a fresh install or after an update: CUDA kernels are compiling. They're cached in CUPY_CACHE_DIR, so the next run is fast.
    setup_env.sh fails with permission denied under /root You aren't root. Run ENV_ROOT="$HOME/.envs" bash scripts/setup_env.sh.

    Connecting¶

    Symptom Cause and fix
    Timeout waiting for GNSS server / Connection refused The server isn't running, the IP is wrong, or a firewall blocks 5555. On the server, check with ss -tlnp \| grep 5555 (Linux) or netstat -an \| findstr 5555 (Windows).
    Works on the server, not from a laptop The server is bound to 127.0.0.1 (GNSS_BIND), or the firewall allows only local traffic.
    Server is busy Another client holds the session. It's released when that client finishes, or after 120 s of inactivity. --status shows the server's state.
    OSError: [Errno 98/10048] Address already in use when starting Another process, often an earlier server, has the port. Stop it, or set GNSS_PORT.
    Remote client hangs or fails on the first frames The server is using the shm transport, which only works on the same machine. Start it with --transport zmq (the start scripts' default).

    Initialisation¶

    Message Cause and fix
    RINEX navigation file not found for date … No navigation file for the scenario date on the server. Download the named file and upload it, or put it in data/rinex/.
    emitter_file not found: … The emitter CSV is missing on the server. The scenario travels to the server; the files it points to don't. What lives where.
    An error loading the trajectory or a pattern Same cause: the path must exist on the server, relative to the server's working directory.
    Trajectory continuity error Two segments don't join within continuity_tolerance_m / _deg. Fix the CSV so that each segment ends where the next begins.
    TypeError or ValueError while loading emitters An empty cell in a column the row's type needs, or an unsupported type (PULSED, SPOOFER) or geometry (TRAJECTORY_FILE). See Emitter CSV.
    no satellite is above the elevation mask Lower elevation_mask_deg, or move start_epoch_utc or the position.

    Recording¶

    Symptom Cause and fix
    Fewer satellites than expected --max-sats (default 12) caps the whole run, in RINEX order, after any per-constellation max_sats. Raise it.
    A jammer has no visible effect Check its type: noise and chirp aren't rendered yet. Check its received power too: power_dbm is transmit power, and path loss over kilometres costs around 100 dB.
    An extra band appeared in the output A jammer's center_freq_hz is nearest to a band with no satellites, so that band was added for it.
    Empty or truncated .bin files The run was interrupted. The session is released on Ctrl+C, but the partial files remain. Record again.
    Disk filled up complex64 is 8 bytes per sample per stream. Use --format sc16 or sc8, a shorter duration_s, or a lower sample rate.
    Changing sample_rate_hz had no effect It's a server setting. Edit the server's config/simulator_params.yaml and restart the server.

    In the receiver¶

    Symptom Cause and fix
    PocketSDR: executable/script not found --pocketsdr must point at the PocketSDR root, which contains app/ or bin/. If the binaries aren't built, add --rx-type trk_py.
    No satellites tracked Check active_sats in recording.json, and that --signals names those constellations.
    A spectrum that looks mirrored, or acquisition failing on sc16/sc8 Integer formats invert Q. Conjugate the samples if your receiver expects the usual convention.
    Ranges off by tens of metres compared with truth Read truth at receiver time + 0.1 s. The recording starts one frame after the scenario start.
    A constant offset between pseudorange and truth That's the receiver's clock bias, which isn't part of the signal. Estimate it once and remove it.
    C/N0 doesn't match hardware It isn't meant to. The output has an ideal noise floor, so compare C/N0 between runs only.

    Still stuck¶

    Collect the server log (stdout, or journalctl -u gnss-server), the client output, the scenario YAML, the server's simulator_params.yaml and the output of --status. Together they almost always show which side failed.
