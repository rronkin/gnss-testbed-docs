    Performance¶

    How fast it runs, what it scales with, and where the time actually goes, from measured runs on two Blackwell GPUs.

    Reading the numbers¶

    The server works in frames of 100 ms of signal. A frame time under 100 ms is faster than real time. Above that, the slowdown is frame time / 100 ms: at 400 ms per frame, a 10-minute scenario takes 40 minutes.

    Term
    GPU time Geometry, shaping, delay, jammers: everything until the frame is ready in GPU memory
    End-to-end GPU time plus the device-to-host copy and the transfer to the client

    The cost of a frame doesn't depend on the scenario's length, and memory doesn't grow with it, so total run time is simply frames × frame time.

    Headline¶

    40 msend-to-end per 100 ms frame: 4 elements, 2 bands, 20 jammers, 6.1 MHz on an RTX 5090
    2.0–2.4×RTX 5090 over RTX PRO 4500, across every configuration measured
    ~60%of a 16-element frame is spent moving data, not computing it
    ~21 Gbpsmeasured sustained transport rate, which caps large arrays

    RTX 5090 vs RTX PRO 4500¶

    Three bands (GPS L1, L2, Galileo E1), 24.6 MHz, May 2026. Each point averages 90 frames after a 10-frame warm-up.

    Elements Jammers per band PRO 4500 GPU RTX 5090 GPU Speed-up RTX 5090 end-to-end
    1 0 46.6 ms 23.4 ms 2.0× 41 ms
    1 100 152.3 ms 58.2 ms 2.6× 76 ms
    4 0 143.6 ms 67.5 ms 2.1× 160 ms
    4 100 487.7 ms 204.2 ms 2.4× 297 ms
    8 0 272.0 ms 122.5 ms 2.2× 306 ms
    8 100 938.1 ms 395.8 ms 2.4× 579 ms
    16 0 532.4 ms 233.3 ms 2.3× 586 ms
    16 100 1,833.8 ms 780.0 ms 2.4× 1,133 ms

    The RTX 5090 has about 4× the raw FP32 throughput of the PRO 4500 but is only 2.3× faster. The workload is bound by memory bandwidth and host orchestration, not arithmetic.

    Hardware: AMD Ryzen 9 9950X with an RTX 5090 (32 GB); RTX PRO 4500 Blackwell (32 GB).

    The transport bottleneck¶

    End-to-end time minus GPU time, on the RTX 5090:

    Elements GPU Transport Transport share Data per frame
    1 23 ms 18 ms 43% 59 MB
    4 67 ms 92 ms 58% 236 MB
    8 122 ms 184 ms 60% 472 MB
    16 233 ms 352 ms 60% 945 MB

    Every frame produces bands × elements × samples × 8 bytes. That volume, not the jammer count, sets the transport cost. At 16 elements the GPU is idle for most of each frame, waiting for the copy. For large arrays, a faster transport helps more than a faster GPU.

    Same-machine clients

    A client on the GPU host can take frames through shared memory (--transport shm), which skips the network serialisation. See Transport.

    Real-time envelope¶

    The largest configurations whose GPU time stays under 100 ms on one RTX 5090, with 16 elements unless noted:

    Signals Fits in real time
    GPS L1 up to 12.3 MHz with 20 jammers (82 ms)
    GPS L1 + L2 up to 6.1 MHz with 20 jammers (79 ms)
    GPS L1 + L2 + Galileo E1 up to 6.1 MHz with 20 jammers (96 ms)
    4 elements, dual-band (CRPA) up to 24.6 MHz with 20 jammers (23 ms)

    These are GPU times. For end-to-end real time on large arrays, the transport above also has to keep up.

    How it scales¶

    Measured on the RTX PRO 4500, GPS L1 only, no jammers (March 2026 build):

    1 element 4 elements 8 elements 16 elements
    GPU time at 6.1 MHz 8.8 ms 17.9 ms 28.1 ms 49.8 ms
    6.1 MHz 12.3 MHz 24.6 MHz
    GPU time, 1 element 8.8 ms 12.5 ms 20.6 ms

    GPU time grows more slowly than the workload at these sizes, because fixed per-frame costs dominate small configurations. Raw compute scales linearly with every dimension:

    \[\text{FLOPs per frame} \approx \sum_\text{bands} N \cdot M \cdot \left(130\,S_\text{sat+BPSK} + 50\,S_\text{CW/FM}\right), \qquad N = F_s \cdot T_\text{frame}\]

    Data volume scales the same way, and for large arrays it is usually the tighter limit.

    What changed since these measurements

    • Shaping (2026-10). Building each baseband once per source left whole-frame time within measurement noise (−17% to +5% at 22 satellites, 1 and 16 elements, 12.3 and 24.6 MHz).
    • BPSK jammers (2026-10) now take the satellite path for exact code timing, so each costs about what a satellite costs. Measured: 50 BPSK emitters × 16 elements went from 301 to 373 ms per frame. The jammer rows above used BPSK jammers, so jammer-heavy cases are now somewhat slower than shown. CW and FM jammers are unchanged.

    Choosing hardware¶

    Use GPU Priority
    Development, overnight runs, CRPA RTX 5090: the best cost and performance measured Any recent GPU will do
    4-element arrays in real time RTX 5090 Same-host client (shared memory)
    16 elements, 3 bands, in real time H100-class and above Transport first: GPUDirect or zero-copy paths
    16 elements at 50 MHz with 200+ jammers, in real time B200 or several H100s Multi-GPU (planned) and transport

    VRAM is never the constraint: even the largest of these fits in about 3.2 GB.

    Measure your own¶

    • Watch simulation_realtime_factor and the GPU, gather and transport timings on the monitoring dashboards while a real scenario runs.
    • scripts/benchmark_runtime.py starts its own server, sweeps a matrix of constellations, sample rates, element counts and jammer counts, and appends the results to docs/benchmarks/benchmark_results.csv. Stop any running server first, since it needs port 5555.
